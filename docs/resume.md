# 断点续跑（P1-4）

长任务跑到一半中断（Ctrl+C、崩溃、断电），`--resume-run` 能从断点接着跑，而不是从头重来。续跑不重放旧工具调用（`prepareResume` 只校验并修复最后一轮未知结果、重建消息历史），并且对已成功的写操作做去重：**不重复执行已经生效的写操作**。

```bash
nyra --resume-run <运行 ID> "继续"
```

## 幂等键

幂等键 = `sha256(工具名 + "\n" + 参数的稳定序列化)`。稳定序列化只排对象键的顺序（数组保序），所以模型两次发同一调用（键名顺序不同）算同一个键；参数里任何一个值变了，键就变了。键里只有哈希，没有参数原文，不会把文件内容、密钥等写进运行记录。

键的落盘：`RunRecorder` 在 `tool_start` 事件里算出键、记在事件的 `args_hash` 字段，`tool_result` 事件也附上同一键（按调用 ID 配对）。续跑时 `loadCompletedWriteKeys` 从 `events.jsonl` 读回：只认 `ok=true`、工具在可核查白名单内、且带 `args_hash` 的调用。

## 哪些写操作可跳过

只含 `verifyWriteApplied` 能读回核查的 5 个工具：

| 工具 | 读回核查 |
| --- | --- |
| `write_file` | 文件内容全文一致 |
| `edit_file` | 文件包含 `new_text` |
| `plan` | `plan.md` 内容全文一致 |
| `memory_append` | 记忆文件包含追加内容 |
| `save_skill` | 技能文件内容一致 |

跳过要同时满足两个条件：**键在已完成集合里，且读回核查仍证明写入已生效**。只凭键命中就跳过会撒谎——中断后文件可能被外部改动或删除。所以：

- 文件现状与参数一致 → 跳过，模型收到“已在中断前成功执行过（幂等键命中），跳过重复执行”。
- 文件被外部改过 / 已删除 → 读回核查失败，正常重执行。
- 旧运行（0.5.2 之前，事件里没有 `args_hash`）→ 不认，照常重执行，不静默跳过。

续跑开始时，stderr 会打一行提示：`续跑幂等：N 个已成功的写操作将被跳过（不重复执行）。`

## 不在范围的工具

`shell`、`apply_patch`、`http_post`、浏览器/电脑操作、`delegate`、MCP 工具**不参与去重**，续跑时照常重执行。原因：相同参数不等于相同结果——命令依赖时间与外部状态、补丁依赖当前文件内容，无法证明重复执行是无操作。宁可多执行一次，也不要静默跳过一次本该做的事。

跳过的调用不进循环守卫的计数（已成功的调用本就不该再被守卫计数），也不触发重复执行提醒。

## 诚实边界

- `args_hash` 是单向指纹：它能证明“某个参数的调用成功过”，但不能还原参数原文。事件落盘的脱敏（32 字符以上的 token 一律打码）对它豁免，否则指纹会被毁成 `[已隐藏]`、续跑再也认不出已完成的调用。
- 跳过只保证“这一次调用已生效”，不保证模型后续步骤仍成立。如果模型怀疑现状变了，可以自行读文件核对——跳过文案会明确告诉它“这是跳过的、不是刚执行的”。
- 幂等键只认“参数完全相同”的调用。模型换一种写法达到同一效果（例如 `write_file` 全文重写 vs `edit_file` 改一行），键不同，会正常执行——这是故意的：去重只做能证明的事。
